## Context

当前生产部署依赖项目根目录中的 `deploy.ps1` 直接执行 `git pull`、`docker compose build` 和 `docker compose up -d`。这套流程没有发布版本号、没有发布清单、没有发布前数据库快照，也没有正式的回滚入口。数据库备份、恢复和迁移虽然有独立 PowerShell 脚本，但没有与发布动作关联，无法保证“代码版本”和“数据库状态”成对管理。

当前项目已经运行在单机 Docker 环境中，应用与 MySQL 容器名称固定，部署入口也已经收敛到 PowerShell。因此最适合的改造方式是继续沿用单机 Docker 形态，在服务器上引入本地发布元数据、版本目录和数据库备份，而不是额外引入镜像仓库、CI/CD 平台或配置管理系统。

## Goals / Non-Goals

**Goals:**
- 为每次生产发布生成唯一版本号，并持久记录发布时间、来源提交、数据库备份文件和发布状态。
- 在发布前自动创建数据库备份，并在发布失败时提供明确的应用回滚与数据库回滚路径。
- 为运维提供统一的 PowerShell 入口，包括发布、状态查看、日志查看和回滚。
- 在发布成功后执行容器健康检查和关键接口校验，失败时阻止发布完成。

**Non-Goals:**
- 不引入远程镜像仓库、蓝绿部署或多机编排。
- 不改造业务功能代码，不新增数据库业务表。
- 不实现自动数据库 schema 双向迁移，仅提供基于 SQL 备份的恢复能力。
- 不替换现有 Docker Compose 运行时模型，仍保持单机 `docker compose` 发布方式。

## Decisions

### 1. 使用服务器本地 release 目录和 manifest 记录版本
发布脚本将为每次上线生成一个时间戳版本号，例如 `20260508-173500`，并在服务器本地维护：
- `releases/<version>/`：该版本的发布产物目录
- `releases/current/`：当前线上版本指针
- `releases/previous/`：上一版本指针
- `releases/manifest.json`：发布历史与回滚所需元数据

选择本地目录而不是仅靠 Git HEAD 的原因是：回滚时需要一个稳定的、已发布过的版本快照，而不是依赖当前工作目录是否被覆盖。

备选方案：
- 直接使用 Git commit 回滚：实现简单，但无法表达发布时的数据库备份与实际生效版本。
- 依赖 Docker 镜像 tag：更标准，但当前环境没有镜像仓库和镜像分发流程，短期落地成本更高。

### 2. 发布采用“同步代码到版本目录 + 在版本目录执行 compose build/up”
发布脚本在服务器上创建新的版本目录，并将当前仓库内容同步进去，在该目录内执行 `docker compose -f docker-compose.prod.yml build` 与 `up -d`。这样每个版本目录都能保留对应的 Compose 文件、Dockerfile 和文档快照。

选择版本目录构建而不是直接修改根目录的原因是：目录即版本，回滚时可直接切换到先前目录重新执行 compose，而不依赖再一次 `git checkout`。

备选方案：
- 仍在根目录构建：简单但没有版本隔离，不能快速定位已发布版本。
- 预构建镜像后仅切 tag：理想但超出当前基础设施约束。

### 3. 发布前强制数据库备份，并把备份文件与发布版本绑定
每次发布前都通过 MySQL 容器执行 `mysqldump`，生成 `backup/db/nav_before_<version>.sql`，并把路径记录到 manifest。这个备份表示“切换到该版本之前的数据库状态”，因此默认回滚时应优先使用当前线上版本记录的备份，而不是盲目使用目标版本自己的备份。回滚脚本允许：
- 仅回滚应用版本
- 回滚应用版本并恢复对应数据库备份

选择强制备份是因为当前项目数据更新频繁，且发布失败后最难恢复的是数据库状态一致性。

备选方案：
- 只备份代码不备份数据库：风险过高。
- 每次只保留一个数据库备份：不利于追踪多个发布点。

### 4. 健康检查采用“容器状态 + HTTP 接口”双重校验
发布成功的判定至少包含：
- `navigation_app` 容器进入 healthy
- `navigation_mysql` 容器处于 healthy 或 running
- `http://127.0.0.1:8991/api/links` 可返回成功响应

选择双重校验是因为容器已启动并不代表应用已能正常提供服务。

备选方案：
- 只检查 `docker compose ps`：无法覆盖应用内部错误。
- 只检查 HTTP：无法发现数据库容器异常。

## Risks / Trade-offs

- [版本目录会占用更多磁盘] -> 保留最近 N 个版本并提供清理策略，数据库备份同样按数量限制。
- [数据库恢复会覆盖线上新数据] -> 回滚脚本默认先确认，并明确区分“仅回滚代码”和“代码+数据库一起回滚”。
- [发布目录切换后可能与固定容器名冲突] -> 仍沿用固定 Compose 服务与容器名，回滚时在目标版本目录重新执行同名 compose，保持容器标识稳定。
- [从工作目录复制文件可能带入不需要的本地内容] -> 同步时排除 `.git`、`node_modules`、`backup`、`openspec` 等无关目录，并优先同步受控文件。

## Migration Plan

1. 重构现有 `deploy.ps1`，将单纯的“拉代码并启动”升级为版本化发布入口。
2. 新增 `rollback.ps1`，读取 manifest 并执行应用回滚，可选恢复数据库。
3. 建立 `releases/` 和 `backup/db/` 目录规范，首次发布时自动初始化。
4. 更新 `DOCKER.md`，替换为新的发布、查看状态、回滚和数据库恢复说明。
5. 在测试服务器完成一次完整发布和一次完整回滚校验。

## Open Questions

- 版本目录是否保存在仓库根目录下，还是独立的服务器部署根目录下；当前实现将默认使用仓库根目录下的 `releases/`。
- 发布时是否需要自动执行 `git pull`；当前实现可保留，但应允许通过参数跳过。
